# 0005. Kustomize base with minikube and ci-kind overlays

Date: 2026-10-26. Status: accepted.

## Context

The same workloads run on a laptop minikube during development and on an ephemeral kind cluster in CI. The differences are small: resources, replicas, image tags, schedule of the drift CronJob and how services are exposed.

## Decision

Manifests live in `k8s/base` with one folder per workload, and two overlays patch them: `k8s/overlays/minikube` (low requests and limits, `latest` images, NodePort for frontend and backend, drift check every 5 minutes) and `k8s/overlays/ci-kind` (minimal resources, images from the CI build). Secrets are generated by `secretGenerator` from a git-ignored env file. Deployment is `kubectl apply -k`.

## Consequences

- No templating language and no extra tool: Kustomize ships with `kubectl`.
- Base manifests stay valid Kubernetes YAML that reviewers can read directly.
- Overlay patches must target resource names exactly; renaming a base resource breaks overlays at build time, which `kubectl kustomize` catches in CI.
- Values that vary a lot between environments would be easier with Helm; revisit if a third environment appears.
